    Why I Still Love Vanilla JavaScript

    Frameworks come and go, but understanding the platform itself never goes out of style. Here's why I keep reaching for plain JS for small projects.

    Every year a new JavaScript framework promises to solve all your problems. And every year I find myself reaching for plain vanilla JS more, not less. Not out of nostalgia - out of pragmatism.

    When you skip the framework, you skip the abstraction layer. That means faster load times, no dependency updates to chase, and debugging that traces straight to platform behaviour. When something breaks, the answer is always in the MDN docs - not in a GitHub issue thread three versions old.

    There is also the knowledge dividend. Every hour you spend understanding the DOM API, event delegation, or the fetch lifecycle is an hour that pays off in every framework you touch afterwards. React and Vue are just thin layers on top of things you already know.

    My rule of thumb: if the project ships fewer than three components and has no shared state, vanilla JS wins. For everything else, I pick the right tool - but I always know what is happening underneath it.

    Building Accessible UIs from Scratch

    Accessibility isn't an afterthought - it's an architecture decision. A walkthrough of the patterns I apply to every project from day one.

    The most common accessibility mistake I see is treating it as a final checklist item - something to bolt on after the UI is "done". By that point, the structural decisions that make accessibility easy or hard have already been made, and they were made without accessibility in mind.

    My starting point is always semantic HTML. A <button> that looks like a link is already a problem. Screen readers, keyboard users, and voice control software all rely on the browser's built-in understanding of what each element is. Div soup with ARIA patches is harder to maintain and easier to get wrong.

    Once the structure is right, I focus on focus management. Opening a modal? Move focus inside it. Closing it? Return focus to the trigger. Navigating between pages in a SPA? Announce the new view to screen readers. These are small habits that compound into a dramatically better experience for keyboard-only users.

    Finally, I test with actual assistive technology - at minimum VoiceOver on macOS and NVDA on Windows. Automated tools catch maybe 30% of real-world issues. There is no substitute for tabbing through your own work with the mouse unplugged.

    My Favourite VS Code Extensions in 2024

    A curated list of the tools that genuinely changed how I write and review code - no fluff, just the ones I actually use daily.

    I have tried dozens of VS Code extensions over the years and uninstalled most of them. What follows is what survived - tools that earn their place in my editor every single day.

    ESLint + Prettier. Non-negotiable on any JS project. ESLint catches logic errors and enforces conventions; Prettier handles formatting so I never argue about it in code review. I configure them once per project and forget about style.

    GitLens. Inline blame, file history, and commit search without leaving the editor. The "who wrote this line and why" question gets answered in seconds. Worth every bit of the startup overhead.

    Error Lens. Surfaces ESLint and TypeScript errors inline on the offending line rather than waiting for you to hover. Sounds minor; it is not. The feedback loop shrinks noticeably.

    Thunder Client. A lightweight REST client inside VS Code. I reach for it whenever I need a quick API call without switching to a separate application. Collections sync via the workspace, so the whole team shares the same requests.
